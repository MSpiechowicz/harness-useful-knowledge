# Desktop expectations for the K4 CLI (from desktop package D1)

The desktop (harness-useful-desktop `business/src/ecosystem/knowledge_review*.rs`, `knowledge_approval.rs`, `knowledge_upgrade.rs`, `knowledge_held.rs`) parses these shapes. K4 must print them, or record a deviation that the desktop then adapts to.

## Documents and listing

- A rename (`docs rename`) of a row that is not live is a change like any other: it takes the next revision (an `approve --expect REV` of the asked revision is then `changed`), a waiting row goes back to draft and the history gets an `edited` event with the comment `renamed`. Renaming a live document that has a pending version renames the pending version the same way.
- An id that names a place the routing does not use (`local:5` with everything remote) is `notFound` for `ask|request-changes|approve|go-live|review|comment`, before anything is opened.
- `docs import --ask` on a file whose text a draft (or a row with requested changes, or a pending version) already has is `unchanged` and still asks that row: the event carries `"asked": true`. With approval off it is refused as before.
- A review's comments carry the revision that was reviewed (`--expect`), not the one the document is at when they are written.

- Document rows carry `status`, `revision`, `pending`, `pendingOf`, `lastChange`. Non-live `docs get` rows also carry `lastRequest`. The desktop also accepts `lastSentBack` and `lastChangesRequested` and renames them to `lastChange`.
- `docs get --json` of a row that is not live adds `"authors": [names]` to the document, and the `pending` object of a live row has the same key for its pending version. They are exactly the people the `selfApproval` and take-back rules count: the row's `updatedBy`, everyone who wrote the version since it was last live (the `drafted`, `edited` (a rename too) and `updateDrafted` events, from every event, not only the newest ones a history lists) and the latest asker. Each person is there once (names that differ only in case count as one, the first spelling is kept). The key is absent when the history could not be read, and a live row has none of its own. The desktop mirrors the rules by comparing the name of the person, trimmed and lower-cased, with `authors`. `docs list` rows carry it only where a reviewer needs it, with the same list and rules: a row whose own `status` is `waiting` has top-level `"authors"`, and a live row whose `pending` version is `waiting` has `"authors"` inside its `pending` object. Every other row (live, draft, changesRequested, or a pending version that is not waiting) has no `authors` key. The people of all such rows of a page are read together (a small constant number of reads, not one per row), and a failure leaves out the `authors` of the page, never fails the list. In list rows `authors` is capped at 20 names (the row's `updatedBy` first, then the writers oldest first, then the latest asker) and is for display and badges: the `selfApproval` and take-back rules always read every name, and `docs get` prints them all. A page of 200 rows can therefore not grow past 20 names a row.
- `docs list --status live|draft|waiting|changesRequested|pending` is only sent when the server lists `docs-drafts`.
- A team database never stores a folder of this computer. A project without a git remote is keyed `path:/absolute/path`, and only a `git:` key leaves this computer. Every write that would link a document in the remote place to a `path:` key is refused with `{"error":"localPath","message":"<folder> has no git remote, so a team document cannot be linked to it (only a git: project key leaves this computer)"}` (exit 1; the message names only the last part of the path). It covers `docs links set` on a remote document, `docs import` into the remote place (the whole import, before anything is opened or written, `replacing` included) and `held approve` into the remote place (the proposal stays held, the user can reject it or approve it with `--place local`). The database itself refuses it too (`put_document` and `set_links` of the PostgreSQL, libSQL and MongoDB stores). This computer's own database keeps `path:` links. A writer that opens a team database deletes any `path:` link an earlier version left there. A document that no link is left on does not become global (which would widen who sees it): it becomes a draft, with an `edited` history event whose comment is `folder link removed`. A live, waiting or sent-back one also gets a new revision (a waiting one needs a new ask) and leaves the agents' reach, and the pending update of a live one is deleted with its chunks, events and comments (the event then says `folder link removed, its pending update was dropped`), so no pending version points at a draft. A draft only gets the event. Promoting a pending version onto a row that is not live is refused. A document that keeps a `git:` link just loses the path link. The writer prints one line on stderr with the count (never a key). A role that may not write only prints a line saying how many links remain and that a teammate who can write will remove them, and changes nothing. Reads never send the key either (a source key built from a folder, `path-…`, is not looked up in the team database either): a search or recall scoped to a `path:` project asks the team database as if it had no repository (the global team documents), and a `docs list --repo path:…` or a title lookup of one does not reach it at all (it holds no such link). This is done in the routed store, the search pipeline and the three team stores.
- Feature tokens: `docs-drafts` and `docs-approval`.

## Transitions, review and history

- Transitions: `docs ask|request-changes|approve|go-live|take-back --json ID --expect REV [--comment TEXT]`.
  - Going live removes the version's comments: `approve` and `go-live` delete every comment (replies included) of the document that goes live, and of both rows when a pending version is promoted onto its live document, in the same transaction as the change. A live document therefore has none to show (`docs comments` of its id is empty), and a new review starts clean. The history keeps its events, with their comments (the overall text of a review). Stored original files are not affected.
  - `take-back` ("Take it back") moves `waiting` → `draft` and records a `withdrawn` event. Only the author may do it: the actor must be the row's `updatedBy` or the latest asker (the `selfApproval` rule turned round, names trimmed and case-insensitive), else `notAuthor`, and a git `user.name` is needed, else `noName`. It works with approval on or off (a row left waiting when approval was switched off can be taken back). It takes no `--comment`. Other refusals: `changed`, `wrongState` (not waiting), `notFound`, `readOnly`, `unreachable`. Reply: the transition shape.
  - Success → `{"id","status","revision","promoted"}`.
  - Refusal → `{"error": code, "message"}`, exit 1.
  - Codes: `notFound`, `changed`, `wrongState`, `approvalOn`, `approvalOff`, `selfApproval`, `notAuthor`, `noName`, `readOnly`, `commentRequired`, `sinceUnavailable`, `refused`, `localPath`.
  - A remote that is down → `{"error":"unreachable"}`.
- Review: `docs review --json ID --expect REV --verdict comment|approve|requestChanges [--body TEXT] [--comments FILE]`.
  - FILE is a JSON array `[{"section","occurrence"?,"side":"old"|"new","from","to","body"}]`. `occurrence` (1-based, default 1) says which of the sections that share the heading `section` is meant, so it is the compare section's `occurrence`.
  - Reply: the same as a transition.
- History: `docs history --json ID` → `{"events":[{"kind","by","at","comment"}],"total"}`.
  - Kinds: `drafted`, `edited`, `updateDrafted`, `asked`, `changesRequested`, `approved`, `wentLive`, `withdrawn`. `sentBack` is also accepted.
- Comments:
  - `docs comments --json ID` → `{"comments":[{"id","reviewId","section","occurrence","side","from","to","body","by","at","parentId","resolvedAt","resolvedBy","revision","outdated","quote"}]}`. `lineFrom`/`lineTo` are also accepted. `occurrence` is `null` for an overall comment and a reply, else a number from 1.
  - `quote` is `[{"line","kind","text","cut"?}]` or `null`. It holds the lines `from..=to` of the comment's `side` as the compare of the reviewed revision showed them, kept when the comment is written (`line` is the number on that side, `kind` is `added`, `removed` or `same`). It is `null` for an overall comment, a reply, a comment written before quotes were kept, and a range the compare did not show. At most 20 lines and 4000 bytes, the rest is cut: the line that crosses the byte cap is kept up to a character and carries `"cut": true` (left out otherwise), and the lines after it are dropped. `outdated` only checks the lines that were kept (the first 20 of a longer range), and compares a `cut` line by its start.
  - `outdated`: overall comments and replies never are. A line comment is when its section (`section` and `occurrence`) is gone from the row it is on, or the lines `from..` of its side now differ from `quote`. Without a quote, a missing section is outdated, else it is outdated when the content changed since the comment was written. The comments of a live row that has a pending version are all outdated (they were about text now live). `old` side lines are read from the live document the pending version replaces.
  - Reply: `docs comment reply --json ID COMMENT_ID --body TEXT` → `{"comment": {...}}`.
  - Resolve: `docs comment resolve|unresolve --json ID COMMENT_ID` → `{"comment": {...}}`.
  - Delete: `docs comment delete --json ID COMMENT_ID` → `{"deleted":[ID,…]}`: the comment and, when it starts a thread, its replies (the comment's id first, ids printed like `comments` prints them, `local:N` for this computer). A reply deletes only itself. Only the one who wrote the comment may (git `user.name`, trimmed, without case): `notAuthor` otherwise, `noName` without a name, `notFound` for an unknown document or comment, `readOnly`, `unreachable`. Works in every state, with approval on or off. The history is not touched.
- Compare: `docs compare --json ID [--since REV]` → `{"live","pending","revision","sections":[FileDiff + occurrence…],"truncated"}`.
  - `revision` is the revision of the row that is reviewed (`pending`): the `--expect` of a review of it.
  - Each section also has `"occurrence"`: counted from 1 among the sections of its version that share its `path`, the unchanged ones included (the old version for a deleted section). `(path, occurrence)` is what a line comment names as `section` and `occurrence`.
  - The section `status` follows the git style: `added`, `deleted`, `modified`. The desktop also maps `removed` → `deleted` and `changed` → `modified`, and drops `same`.

## Files, approval, upgrade and stats

- Download: `docs download --json ID --to PATH [--live]` → `{"path","original":bool}`.
  - Without a stored original the text goes to `PATH` with its extension adjusted to `.md` or `.txt`. When that adjusted path exists already the command refuses with `refused` and writes nothing: only `PATH` was confirmed by the user. `PATH` itself is replaced as before.
- Approval:
  - `approval get --json` → `{"approval","place","writable","changedBy","changedAt"}`. `changedBy` is the git `user.name` of whoever last switched it, `changedAt` an RFC 3339 UTC time. Both are `null` while unknown (never switched, or by an older server).
  - `approval set --json on|off` → the same shape. It needs a git `user.name`, else `noName`, and records who and when atomically with the switch. The checks run in this order: `refused` (no team database), `unreachable`, `readOnly`, `noName`.
- Upgrade: `upgrade --json` → `{"upgraded":bool,"waiting":bool}`. `waiting` means a role without the permission can't upgrade (a read-only role, SQLSTATE 42501, an unauthorized or forbidden token). Any other failure (a timeout, a database that does not match) is an error `{"error":"failed","message"}`, not a wait.
- Stats: top-level `drafts`, `waiting`, `pending`, `approval`, and per place `drafts`, `waiting`, `pending`.
  - Top level also has `"me": {"name": string|null}`: the git `user.name` of the folder `stats` runs in (the viewer's identity), `null` when there is none.

## Import and held

- Import manifest: `draft`, `ask`, `note`. Each file event: status `pending` and a `draft` bool.
- Held:
  - Items carry `addedBy` (a string), top-level `status` (`waiting`|`changesRequested`) and, while `changesRequested`, a top-level `comment` (the reviewer's text, also kept in the nested `changesRequested: {comment, at, by}`). A waiting item has no `comment`.
  - `held list --json [--sort created|addedBy]`: `created` (default) is newest first. `addedBy` sorts by the `addedBy` name ascending, case-insensitive and trimmed, proposals with no (or an unshowable) name last, each group newest first. Anything else is a usage error.
  - `held request-changes --json ID --expect REV --comment TEXT`.
  - `held reject … [--comment TEXT]`.
  - Approve may answer `pending`, or `added` with `"draft": true`.
